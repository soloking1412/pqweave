# BIP-360 (P2MR) migration reference

Reference implementation of Pay-to-Merkle-Root output construction and the
migration path into it, so wallets can adopt one tested library instead of each
writing this again under time pressure.

> **BIP-360 is `Status: Draft`.** It was merged into `bitcoin/bips` in February
> 2026, which means it meets documentation standards for discussion — not that it
> is activated, scheduled, or endorsed. **No network enforces P2MR rules today.**

## The hazard you must understand first

Under BIP-141 forward compatibility, witness versions 2–16 are **anyone-can-spend**.
P2MR occupies witness version 2. So until BIP-360 activates:

**Real coins sent to a `bc1z…` address can be taken by anybody, permanently.**

This is not a privacy nuance or a "not recommended" — it is unrecoverable loss.
`@scure/btc-signer` independently refuses to build such an output unless you pass
`allowUnknownOutputs`, warning "there is a chance that input is unspendable".

Accordingly, this library **refuses** to build a mainnet P2MR migration:

```ts
planP2mrMigration({ ..., target: 'bitcoin' });
// throws P2mrNotActivatedError, even with acknowledgeAnyoneCanSpend: true
```

Test networks are allowed, but still require an explicit acknowledgement so the
risk is never implicit:

```ts
planP2mrMigration({ ..., target: 'signet', acknowledgeAnyoneCanSpend: true });
```

## What P2MR is

P2MR is Taproot with the quantum-vulnerable key path removed.

A P2TR output commits to a _tweaked public key_. That key is visible in the
output itself, which is why a Taproot address is exposed to Shor's algorithm from
the moment it is funded, not merely when it is spent.

P2MR **omits the internal key entirely** and commits only to the Merkle root of a
script tree. There is no key in the output, so there is nothing for a quantum
attacker to recover from it.

### Wire format

| Item          | Value                                                                |
| ------------- | -------------------------------------------------------------------- |
| scriptPubKey  | `OP_2 OP_PUSHBYTES_32 <32-byte merkle root>` (34 bytes)              |
| Witness ver.  | 2                                                                    |
| Address       | bech32m — `bc1z…` mainnet, `tb1z…` testnet/signet, `bcrt1z…` regtest |
| Merkle hashes | BIP-341 tagged hashes (`TapLeaf`, `TapBranch`)                       |
| Control block | `1 + 32*m` bytes; **parity bit always 1** (no key path exists)       |

### A note on the address prefix

Many secondary sources say P2MR addresses start with **`bc1r`**. They are quoting
an **older draft**. bech32m encodes the witness version as the first data
character: `q`=v0, `p`=v1 (Taproot), `z`=v2, `r`=v3. The current BIP specifies
witness version 2, so the prefix is **`bc1z`**.

The BIP publishes this example address, which this library round-trips exactly
(see `test/bitcoin-p2mr.test.ts`):

```
bc1zzmv50jjgxxhww6ve4g5zpewrkjqhr06fyujpm20tuezdlxmfphcqfc80ve
  → witness v2, program 16d947ca4831aee76999aa2820e5c3b48171bf4927241da9ebe644df9b690df0
```

If your implementation produces `bc1r`, you built against the old draft.

## Why there are no post-quantum signatures here

**BIP-360 does not define any.** They are deferred to a companion BIP, to be
added through the `OP_SUCCESSx` upgrade mechanism so that signature algorithms
(ML-DSA, SLH-DSA) can activate separately.

So this library ships exactly one leaf template:

```ts
rawLeafTemplate(script); // uses the script you supply, verbatim
```

There is deliberately **no** `mlDsaLeafTemplate` or `slhDsaLeafTemplate`. The
opcodes they would need do not exist in any specification yet, so shipping them
would be a guess dressed up as a standard. When the companion BIP lands,
implementing `PqLeafTemplate` is the only change required:

```ts
interface PqLeafTemplate {
  name: string;
  describe(): string;
  buildLeafScript(): Uint8Array;
}
```

## Usage

```ts
import {
  p2mrMerkleRoot,
  encodeP2mrAddress,
  p2mrScript,
  planP2mrMigration,
} from '@pqweave/sdk/bitcoin';

// 1. Build the script tree. Leaf scripts are yours to define.
const tree = p2mrMerkleRoot([{ script: myLeafScript }, { script: myRecoveryScript }]);

// 2. Derive the output.
const address = encodeP2mrAddress(tree.root, 'signet'); // tb1z…
const script = p2mrScript(tree.root); // OP_2 <root>

// 3. Plan a migration from existing UTXOs.
const plan = planP2mrMigration({
  inputs, // same shape the evacuation kit uses
  leaves: [{ script: myLeafScript }],
  feeRate: 4, // sat/vB
  target: 'signet',
  acknowledgeAnyoneCanSpend: true,
});
// plan.psbtBase64, plan.destination, plan.signability, plan.warnings
```

Each leaf comes back with the Merkle path and a ready-made control block for the
eventual script-path spend:

```ts
tree.leaves[0].path; // sibling hashes, leaf → root
tree.leaves[0].controlBlock; // 1 + 32*m bytes, parity bit set
```

## What is inherited from the evacuation kit

`planP2mrMigration` delegates input construction to `prepareSweepInputs`, the
same code the evacuation kit uses. Migrations therefore inherit, rather than
re-implement:

- `nonWitnessUtxo` for legacy and wrapped-SegWit inputs
- `redeemScript` for wrapped SegWit, `tapInternalKey` for Taproot
- `bip32Derivation` so hardware wallets can identify their keys
- **fail-loud behaviour** — an input that cannot be made signable throws rather
  than producing a broken PSBT
- RBF sequencing

## Honest limits

- **BIP-360 is a draft.** It may change again; it has already been renamed twice
  (P2QRH → P2TSH → P2MR) and had all PQ signatures stripped out in July 2025.
- **No end-to-end spend can be demonstrated anywhere.** Not on mainnet, not on
  signet — no public network implements the rules. What is demonstrable is that
  the outputs and migration transactions are structurally correct against the
  specification, and that the tooling refuses to risk funds before activation.
- **Spending _from_ a P2MR output is not implemented**, because it cannot be
  validated by any node. The evacuation kit throws a clear error if you try.
- This library commits to a script tree. It does not make Bitcoin quantum-safe;
  that requires the consensus change this BIP proposes plus the signature BIP
  that follows it.
